Example review: tighten the path policy

A sample PR review guide. Each module explains one coherent part of the change, asks you questions first, and then shows proposed findings for you to agree or disagree with.

Request flow through the policy

The change routes every source read through PathPolicy.check. It still uses check_name for paths that exist only in the base commit, such as deleted files.

Why does the Changes view use check_name instead of check for a deleted file?

  1. The file no longer exists at the head commit, so it cannot be resolved on disk, but its name must still pass the rules.
  2. Deleted files are always safe to show.
  3. check is too slow for diffs.

check resolves the path in the worktree, which is at head. A deleted file is only in the base, so it can be validated by name alone.

Secret patterns match case-insensitively, but extensions do too

Scenario: a file named NOTES.MD is accepted, because the extension is lower-cased before the allowlist lookup. That is intended, but nothing tests it.

Evidence: is_source_name lower-cases the suffix.

Impact: low. Suggest adding a regression test.

Could we add a test that pins case-insensitive extension matching (e.g. `NOTES.MD`)? It's intended behaviour but currently untested.

Server routing

The token check happens in Handler._route, before any route-specific code runs.

RouteTokenNotes

Which check runs first for a request?

  1. The token check.
  2. The Host header check.
  3. The path policy.

_dispatch rejects unexpected Host headers before it looks at the path.

HEAD requests are routed like GET

Scenario: a HEAD to an API route computes the full response and then discards the body.

Impact: negligible on loopback. Mentioned so you can disagree.

Nit: HEAD runs the full GET handler. Fine for loopback; no change needed unless you prefer a 405.
