Quizzler onboarding

Quizzler teaches a repository, or a pull request, in small interactive modules. This guide walks through Quizzler's own code. Each module ends with questions. Rate how confident you are in each answer, because the next version of the guide adapts to those ratings.

What Quizzler is, and your study plan

In one minute

  • What it does: Quizzler turns a repository, or a pull request, into an interactive guide you work through in small modules.
  • How: Claude writes a static HTML guide. A small local server shows it next to the real source, and your answers shape the next version.
  • Stack: Python standard library, plain JavaScript, Git. No framework and no build step.

One engine, two entry points

Key points

  • /onboard teaches a repository. /review-pr <N> teaches a pull request and collects your review.
  • Both produce the same thing: a static HTML guide that loads app/guide.js and app/guide.css.
  • A small local server, GuideApp, serves the guide and gives the browser read-only access to source.

Highlighted code like GuideApp is a link: the code pane on the right shows it, and follows along as you scroll.

The command-line tools sit next to the server:

check.pyDrift gate: anchors, symbols, guide contract, exercise outputs.

progress.pyClassifies answers, writes progress, bumps guide versions.
check_layout.pyHeadless browser check for broken diagrams and narrow-screen layouts.

You are halfway through reviewing PR 42. Where are your answers and comment drafts stored?

  1. In a tracked file under docs/onboarding/reviews/ so teammates can see them.
  2. In docs/onboarding/local/reviews/pr-42/, which Git ignores.
  3. As draft review comments on GitHub.
  4. Only in the browser tab, and lost on reload.

The server saves the results next to the review guide under local/. results_path_for never returns a path outside local/, and nothing is sent to GitHub until you say so explicitly.

What do /onboard and /review-pr have in common?

  1. Nothing. They are separate tools that happen to live in one repository.
  2. Only the stylesheet.
  3. The same guide engine, the same server, and the same guide document contract. Review mode adds Changes and Review views.

The data-mode attribute on <main data-guide> switches review features on. Everything else is shared.

The server's security boundary

Key points

  • The server is small and uses only the standard library.
  • Four layers stand between a web page and your files. Each one is listed below.

The four layers

  1. Loopback only. It binds to 127.0.0.1, and _host_ok rejects any other Host header, which blocks DNS-rebinding tricks.
  2. Per-run token. Each process picks a fresh random token. Every route except /healthz lives under /t/<token>/, and the token is compared in constant time.
  3. Path policy. PathPolicy refuses traversal, hidden components, secret-looking names such as env.storage.*, the guide's own local/ state, and non-source file types. After resolving symlinks it checks the real path again.
  4. Registered exercises only. The browser sends only an exercise name. Names that the active guide does not register get a 404. Registered exercises run in a constrained subprocess.

The token check, in full

Every request goes through _route first:

  • No /t/ prefix: None, which becomes a 404.
  • Wrong token: also None. A wrong token looks exactly like a missing page.
  • Right token: the rest of the path is routed.

Deep dive: the token is compared with hmac.compare_digest, so the time a comparison takes does not reveal how many leading characters were right.

A page on another site tries to load http://127.0.0.1:PORT/app/guide.js without the token. What happens?

  1. The file is served, because static assets are public.
  2. 404. Without a valid /t/<token>/ prefix, every route except /healthz is "not found".
  3. A redirect to a login page.

_route returns None for anything outside the token prefix, and the dispatcher turns that into a 404. Even asset paths need the token.

Someone commits docs/notes.md as a symlink to .git/config. What does the source pane show for docs/notes.md?

  1. The contents of .git/config, because the requested name passes every rule.
  2. A refusal. The policy checks the resolved path again, and the .git component is hidden.
  3. An empty file.

PathPolicy.check resolves symlinks, confirms the result is inside the root, and then runs the component rules again on the resolved path.

What can the browser make the server execute?

  1. Any Python snippet posted to /api/exercise/run.
  2. Any file in an exercises/ directory.
  3. Only exercises that the active guide registers with data-exercise and that exist on disk.

The registry is built once, when the server starts, from the guide's data-exercise names. The request body carries only a name.

Guides that cannot silently rot

Key points

  • Every claim about code is anchored to the source with a data attribute.
  • CI re-checks every anchor, listing and exercise output on every push.

The anchors

AttributeMeaningChecked by
data-src + data-refLiteral text that must appear exactly once in the file. Add data-occurrence when the text repeats.resolve_anchor
data-src + data-symA function, class or constant that must still exist.find_symbols
data-exerciseA registered exercise with a PREDICT: docstring and recorded output.check_exercises
data-finding + data-linesA proposed review finding anchored to a line range at the reviewed head SHA.preview

What fails the build

  1. A literal anchor no longer matches, or matches more than once.
  2. A symbol was renamed or deleted.
  3. A code listing shows a line that is not in the file any more.
  4. An exercise prints something different from expected/.

Each one stays failing until the guide or the recording is updated on purpose.

Deep dive: listings may leave lines out. listing_drift only requires that every line shown appears in the file, in the same order.

A guide anchors on return None, which appears three times in the file, and sets no data-occurrence. What does check.py do?

  1. It uses the first match.
  2. It reports an error: the anchor is ambiguous and lists where it matched.
  3. It prints a warning and passes.

An ambiguous anchor can quietly point at the wrong code, so it fails. Make the literal longer, or pick the occurrence explicitly.

You change PathPolicy so that .svg files are refused. What happens in CI?

  1. It passes for this change, but any exercise whose printed output changes fails until expected/ is re-recorded with --update-expected.
  2. CI updates expected/ by itself.
  3. Nothing is checked, because exercises are only for learners.

The path_policy exercise does not print an .svg case, so its recording still matches. If a change alters printed output, re-recording is a deliberate, reviewable diff to expected/.

The adaptive loop and PR review

Key points

  • Your answers and confidence ratings decide what the next guide version teaches.
  • Review mode follows the same loop, one module of the PR at a time, and never posts on its own.

One turn of the loop

  1. You answer a module's questions. The server saves them under local/, or you paste the QUIZZLER-ONBOARD result code.
  2. classify sorts each answer into one of four groups (table below).
  3. progress.py bump archives the guide, increments data-version, and marks mastered questions data-retired.
  4. Claude rewrites the weak spots from progress.py report.
SureUnsure or guessing
Rightmastered: retire the questionfragile: reinforce it
Wrongmisconception: confront the wrong modelgap: teach it from scratch

In review mode

  • Proposed findings stay locked until you answer the module's questions, so you form your own view first.
  • review.py preview binds every comment marked ready to the reviewed head SHA.
  • Posting is not part of the tool. It needs your separate, explicit instruction.

You pick the right answer but mark it "Guessing". How is that recorded?

  1. mastered
  2. fragile
  3. gap
  4. misconception

A right answer without confidence is fragile. The question stays in the next version, usually with a varied framing.

You mark three findings "Ready" and Claude runs review.py preview. What has been posted to GitHub?

  1. The three ready findings, as one review.
  2. Nothing. Posting needs a separate, explicit instruction after you have seen the exact text and targets.
  3. One summary comment.

Finishing a review never implies permission to post. The preview gives the exact file, lines, SHA and text, so you can decide.
